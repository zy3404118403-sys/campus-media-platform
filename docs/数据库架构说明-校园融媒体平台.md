# 校园融媒体平台 · 后端数据库架构说明

> 2026-10-15 · 基于 `db.js`（866 行）+ `lib/sessions.js` + 本地 dev 库实况核查  
> 一句话定性：**零依赖的原生 SQL 数据层**——不用 ORM、不用迁移框架，Node 22 内置 `node:sqlite` 直连单文件 SQLite，全部 SQL 手写 + 自研幂等迁移机制。

---

## 一、技术底座

| 项    | 实现                                                                     |
| ---- | ---------------------------------------------------------------------- |
| 驱动   | **node:sqlite**（Node 22 内置 `DatabaseSync`，同步 API），**零 npm 依赖**         |
| 存储   | 单文件 `data/campus.db`，伴生 `-wal` / `-shm` 文件                             |
| 并发   | **WAL 模式**（写不阻塞读）+ `busy_timeout=5000`（锁竞争等 5 秒）+ `synchronous=NORMAL` |
| 密码存储 | `crypto.scrypt`（64 字节，`salt:hash` 格式），旧明文数据启动时**自动哈希迁移**               |
| 会话   | `sessions` 表（独立模块 `lib/sessions.js`：token / user_id / last_access）     |
| 备份   | 云端计划任务每周一 03:00 `VACUUM INTO` 日期戳文件 → 自动清理 30 天前                       |

## 二、演进机制（核心设计）

**没有独立的 schema 版本表**，靠两层幂等机制实现"拷贝文件即部署、重启即迁移"：

1. **版本化迁移 v1 → v6**：建表 / 种子 / 结构升级分段执行，全部幂等（`IF NOT EXISTS` / 先检测后执行 / `DROP+CREATE` 可控重建），每次启动自动跑一遍
   | 版本 | 内容                                                    |
   | -- | ----------------------------------------------------- |
   | v1 | 基础：学院 / 用户 / 素材 / 活动 / 招新                             |
   | v2 | 文稿系统 + 新媒体矩阵（三级审核链路）                                  |
   | v3 | 校园社区（博客 / 论坛 / 树洞 8 板块 / 校园墙）                         |
   | v4 | 创作任务 + 贡献值体系（tasks / task_claims / contribution_logs） |
   | v5 | 免登录公开分享（material_shares）                              |
   | v6 | FTS5 统一搜索（search_src + search_fts + 触发器同步）            |
2. **列级热迁移 `ensureColumn`（25 项）**：`ALTER TABLE ADD COLUMN` 自动补列——云端部署新版本时新列**随重启自动生效**，无需人工执行 SQL。覆盖：`users.role / totp_secret / totp_enabled / backup_codes`、`materials.featured / drive_url / sub_type`、`activities.capacity / location / sign_in_code`、`articles.scheduled_at` 等。

## 四、全文搜索子系统（架构亮点）

- **`search_src` 统一源表**：type / ref_id / status / title / body / tags——把素材、博客、帖子、墙贴**四类内容归一索引**
- **`search_fts`**：FTS5 虚拟表，**trigram 分词**（支持中文子串匹配；查询 ≥3 字走 FTS + bm25 相关性排序 + snippet 片段，<3 字自动 LIKE 兜底，FTS 异常降级——搜索永不 500）
- **14 个触发器双向同步**：业务表写入自动维护索引（4 类型 × INSERT/UPDATE/DELETE + 标签表 2 个），数据永不脱节

## 五、代码层典型模式

- **预编译语句**：`db.prepare(...).get / all / run` 全量使用（SQL 注入面为零）
- **统一脱敏出口**：`publicUser()` 等函数保证密码、2FA 密钥、学号等永不出接口
- **状态机 + 日志表**：materials.status 配 material_status_logs，articles 配 article_versions / publish_logs——**全程可追溯**

## 六、优势与局限（结合本项目场景的完整评估）

### 优势

| # | 优势            | 本项目中的实证                                                                             |
| - | ------------- | ----------------------------------------------------------------------------------- |
| 1 | **零依赖、供应链极简** | 驱动是 Node 22 内置（升级 Node 即升级驱动），无任何 npm 依赖 → 无第三方漏洞链、无版本冲突，安全面只有自己的代码                 |
| 2 | **部署/迁移极简**   | 单文件 + 幂等迁移 = "拷贝即部署"；云端阶段二 8 批路由重构 + 阶段三多批上线，**零人工 SQL、零迁移脚本回滚**                    |
| 3 | **WAL 并发设计**  | 写不阻塞读——管理员审核写入时，前台列表/搜索不受影响；`busy_timeout=5000` 兜底锁竞争                               |
| 4 | **全文搜索原生能力**  | FTS5 + trigram 免引入 ES / Meilisearch 等外部服务（对小站是巨大简化），中文子串搜索 + bm25 排序 + 自动降级         |
| 5 | **可追溯模型**     | 状态机字段 + 专用日志表（material_status_logs / article_versions / publish_logs）——审核全程留痕"天然成立" |
| 6 | **备份与灾备简单**   | `VACUUM INTO` 一个文件即全量备份；本地镜像 md5 双向对账、随时可整体回灌                                       |
| 7 | **成本为零**      | 零许可成本、零数据库服务运维（无独立 DB 进程/内存开销），与服务器试用期迁移场景天然适配                                      |

### 局限与代价（诚实评估，均注明"是否已兜住"）

| # | 局限                    | 实际影响                                                                | 兜底/评估                                                                      |
| - | --------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1 | **单写者模型**（SQLite 硬约束） | 写操作串行排队                                                             | 校园规模（千级用户、低频写）完全够——单机写吞吐通常数千次/秒级，本场景日写量远低于此；若未来出现"秒杀式报名"级写并发需评估            |
| 2 | **无法水平扩展**            | 不能多实例负载均衡（文件锁）                                                      | 当前单实例部署（nssm 服务）与之吻合；**若未来做双机热备/多实例，必须换 Postgres/MySQL**——这是最明确的"架构升级触发条件" |
| 3 | **无 ORM / 无类型层**      | <u>SQL 手写全凭自律；`TEXT` 常存 JSON（images / tags / backup</u>_codes）缺结构约束 | 全量预编译语句已把注入面清零；类型安全靠代码规范                                                   |
| 4 | **无 schema 版本表**      | 靠幂等 DDL 替代；每次启动跑一遍结构检查                                              | 量小无感；但"改列类型/重建表"类复杂变更无现成机制，需手工写迁移段（ensureColumn 仅覆盖加列）                     |
| 5 | **备份粒度为全量**           | 无增量 / 无时间点恢复（PITR）                                                  | 每周自动备份 → RPO 最长一周；对内容平台可接受，若要更高可加密（如每日快照）                                  |
| 6 | **内存型会话状态**           | 2FA 挑战等存内存，重启即失效（fail-closed）                                       | 单实例场景为**安全方向**的权衡（用户重走登录）；多实例化时需迁到 DB                                      |
| 7 | **生态工具受限**            | 现成 BI 工具对接不便                                                        | 数据看板已自研（Chart.js），当前无缺口                                                    |
| 8 | 小技术债                  | 过时注释 1 处（L41）、activities 两处重复 ensureColumn                          | 均无功能风险，建议顺手清理                                                              |

### 一句话总结

**在"单实例 + 校园规模 + 一人维护 + 零预算"的约束下，这套选型是近乎最优解**；它的所有局限都有一个共同的换挡点——**当出现"多实例部署"或"显著写并发"需求时，就是迁移到 Postgres 的信号**，届时数据层（db.js 全部 SQL 手写、无 ORM 绑定）反而比用了 ORM 的系统更容易迁移。
